# 1. Query Response Time

이 책의 목적
- 우리가 뛰어난 `MySQL performance`를 달성하도록 돕기 위한 방법을 여러 각도에서 살펴본다. 
- 이 책의 대상은 DBA가 아닌 MySQL을 사용하는 바쁜 실무자. 최소한의 노력으로 최대한의 결과를 얻어야하는 사람. 

Query Response Time
- mysql이 query를 실행하는데 걸리는 시간
   - mysql이 query를 받는 순간 시작해서 result set을 모두 전송한 순간 끝난다.
- mysql performance는 `query response time`에서 시작한다. 

1장은 책 전체의 토대이다. 이후 장에서 response time을 개선하는 방법을 배울 수 있도록 먼저 그 의미를 자세히 설명한다. 

## 동기 부여를 위한 재미난 실화 하나 
2004년 당시 performance를 문제를 해결하는 최첨단 방법은 '고객에게 RAM을 더 판매하라' 였다. 

저자는 기술적으로 더 깊이 파고들어서 문제를 해결. (index 누락)

20년간의 경험을 바탕으로 mysql performance를 다루는 문제가 이 책의 best practice와 technic으로 해결되는 경우가 많다는 것을 배웠다. 

## North Star
mysql이 아니라 application을 전문적으로 하는 engineer에게 performance를 개선하기 위해서 고려해야하는 여러 케이스 (예: RAM, CPU, Storage IOPS, Noisy neighbor 등)를 고려해야하는게 벅찰 수 있다. 

그럴때는 `query response time` 부터 살펴봐라. 
- 이 지표는 의미가 있고 (meaningful)
   - 우리가 직접 경험하는 유일한 메트릭 
- 행동으로 옮길 수 있다 (actionable)
   - 우리가 서비스 코드를 소유하고 있고, query도 변경할 수 있기 때문에 response time 개선은 곧바로 행동에 옮길 수 있는 대상이다. 

mysql performance의 north start인 query response time 개선에 집중하라. 문제 해결에 hardware부터 쏟아붓지 말아라.
1. query metric을 통해서 mysql 이 무엇을 하는지 파악하고 
2. 느린 쿼리를 분석하고 최적화해 response time을 줄인 다음
3. 이 과정을 반복해라 

## Query Reporting
우리가 mysql 을 개선하려면, 
1. 쿼리를 최적화 해야한다 
2. 최적화를 하려면 쿼리가 어떻게 실행되는지 알아야한다. 
3. 어떻게 실행되는지 알려면, query report와 metadata를 비롯한 관련 정보를 바탕으로 쿼리를 분석해야한다. 

query metric 자체는 다른 metric과 마찬가지로 raw value에 불과하다. 엔지니어가 의미를 파악하고 읽을 수 있는 방식으로 수집하고, 집게하고, 보고되어야한다. 

### Sources
쿼리 메트릭은 `slow query log` 또는 `performance schema` 에서 나온다. 
- slow query log: disk의 로그 파일
- performance schema: `performance_schema` 라는 이름이 데이터베이스

쿼리 메트릭을 얻는 가장 좋은 source는 `performance schema`다. 
- 모든 mysql version과 distribution에 존재
- local, cloud 에서 모두 작동
- 이 장에서 다룰 핵심 metric을 모두 지원 
- mysql 분석에 쓸 수 있는 다른 data도 풍부하게 제공한다

### Aggregation
쿼리 메트릭은 쿼리 별로 묶여 집계된다. 
- 쿼리별로 묶는 것이 응답시간이 가장 느린 쿼리를 찾기 좋은 방법이다. 이것이 쿼리 리포팅과 분석의 토대다. 

쿼리 고유 식별을 위한 변환 과정
1. `sql statement`: SQL 구문
2. `digest text`: 쿼리에서 값을 `?` 로 치환
3. `digest hash`: 'digest text'를 SHA-256 

논리적으로 같은 쿼리를 서로 다른 syntax로 동적 생성하자 말아야한다. 서로 다른 digest로 정규화되어 별개의 쿼리로 보고된다. 
```sql
-- 아래 2개 쿼리는 다른 쿼리이다. 
select name from captains where last_name = 'picard';
select name from captains where last_name = 'picard' and first_name = 'john'

-- 아래 2개 쿼리는 같은 digest로 정규화 된다. 
select `name` from start_ships where class in ('galaxy');
select `name` from start_ships where class in ('galaxy', `intrepid`);
```

### Reporting
거의 쿼리 메트릭 도구는 data를 `query profile` 과 `query report` 라는 2단계 구조로 보여준다. 

#### Query profile
개념
- query profile은 느린 쿼리를 보여준다. 
- 정렬 기준의 보편적인 기본 값은 query time이다. query time으로 정렬하면 어디서 시작해야하는지, 즉 가장 느리고 시간을 많이 소비하는 query가 무엇인지 알 수 있다. 

total query time
- query time을 집계하는 방식 중 가장 흔한 aggregate value
- total query time은 query 별 execution time의 합. "mysql이 가장 많은 시간을 들여 실행한 시간은 무엇인가?"

percentage execution time
- query 별 total query time을 모든 query의 전체 실행 시간으로 나눈값. 
- 전체 실행 시간에서 해당 쿼리가 차지하는 비율이 나온다. 

query load
- query 별 total query time을 clock time, 즉 측정 구간의 초 단위 시간으로 나눈 값. 
   - 측정 범위가 5분이고, total query time이 250.2초라면 load는 `250.2 / 300 s = 0.83` 이다. 

#### Query Report
개념
- query 하나에 관해 알 수 있는 모든 것을 보여 준다. 
- query reporting의 두번째 단계이며, 보통 query profile에서 느린 query 하나를 선택해서 연다. 
- 모든 query metric과 metadata를 제공한다. 

`query profile` 로 느린 쿼리를 확인하고, `query report` 로 세부 메트릭을 추출해서 `query analysis` 를 진행한다. 

## Query Analysis
쿼리 분석의 목적은 느린 응답 시간을 해결하는 것이 아니라 쿼리 실행 (=query execution)을 이해하는 것이다. 응답 시간을 해결하는 것은 query analysis 이후에 query optimization 단계에서 한다. 

쿼리 분석에서 고려해야하는 것들 
1. query metrics
2. metadata & application
3. relative values
4. average, percentile, maximum

### 1. Query Metrics
아래 9개의 metric은 query analysis에 필수이고, performance schema는 이를 모두 제공한다. 

#### Query time
개념
- 가장 중요한 metric 
- lock time이 포함된다 

#### Lock time
개념
- query execution 중 lock을 획득하는데 사용한 시간.
- 이상적으로는 query time에서 (=query time에 포함된다) 차지하는 비중이 아주 작아야하는데, 상대적이다. 
   - query lock time이 40~50% 라고 하면 굉장히 커보이지만, query의 실행시간이 160μs 라면, lock time은 길다고 볼 수 없다. 

mysql server가 관리하는 lock
- table, table lock
- metadata lock (mdl)
   - schema, table 등에 대한 접근을 제어한다
   - 구조에 대한 접근을 제어
   - query가 끝날 때가 아니라 transaction이 끝날 때 해제된다. 

storage engine이 관리하는 lock
- row-level lock

performance schema의 lock time 
- 포함: table lock await, metadata lock await
- 미포함: row lock await
- 'row lock await'가 중요하기 때문에 큰 의미가 없다

쓰기에서의 lock time
- row를 쓰기 전에 lock을 걸기 때문에 주로 write 연산에 사용된다. 
- write response time은 부분적으로 lock time에 좌우된다. 
- row lock 획득 시간은 같은 또는 인접한 row에 동시 접근하느 query 수인 concurrency 에 따라 달라진다. 
   - hot row라면 lock time이 response time에 상당 부분을 차지한다. 

조회에서는 lock time
- locking read, 특히 `select ... for update` 는 피해야한다. 
- `select ...for share` 도 shared lock을 획득하는데, 같은 조회끼리는 문제 없지만 x-lock 과는 동시 실행이 불가능하기 때문에 인접한 row에 대한 write를 막는다. 
- `nonlocking read(일반 select)`도 metadata lock과 table lock은 획득하기 때문에 lock time이 0은 아니다. 
   - `alter....algorithm = inplace, lock=none` 으로 하더라도 마지막에는 기존 table sturucture와 새 table structure를 swap 해야하는데, 이때 MDL이 걸린다. 그래서 부하가 많은 곳에서는 select 의 lock-time이 튈 수 있다. 

lock에 대한 5가지 설명 
- `innodb_lock_wait_timeout` 은 row lock에 개별 적용되므로 전체 lock time은 이것보다 클 수 있다. 
- locking과 transaction isolation level은 관련이 있다. 
- innodb는 write하지 않은 row를 포함해 모든 row에 lock을 건다. 
- lock은 transaction commit 또는 rollback 때 해제되며, 때로는 쿼리 실행 도중에도 해제된다 
- innodb에는 record, gap, next-key 등 여러 종류의 lock 이 있다. 


#### Row examined
개념
- msyql이 일치하는 row를 찾기 위해 접근한 row 수
- query 와 index의 selectivity(선택도)가 높을수록 mysql이 일치하지 않는 row를 검새하며 낭비하는 시간이 줄어든다. 

#### Rows sent
개념
- client에 반환한 row 수. 즉, result set size

row-examined 와 비교
1. rows sent = rows examined
   - table row 대비 비율이 상대적으로 작고, 응답 시간도 만족스럽다면 이상적인 쿼리
   - 값이 너무 크다면 table scan을 하고 있을 가능성이 높다
2. rows sent < rows examined
   - 선택도가 낮은 값으로 조회가 되고 있을 수 있다. 
   - 응답 시간이 느린 원인일 수 있다. 
3. rows sent > rows examined
   - 특수 케이스. 고려하지 말자. 

#### Rows affected
개념
- insert, update, delete 된 row 수 

#### Select scan
개념
- 처음 접근한 table에서 발생한 full table scan 수 
- 보통 0 또는 1. 0이 좋은 것이고, 1이면 최적화 필요 

#### Select full join 
개념
- join 된 테이블에서 full table scan이 발생한 수 
- Select scan 보다 더 나쁘고, 반드시 최적화 되어야한다. 

#### Created tmp disk tables
개념
- disk에 생성된 temporary table 수.
- disk access는 memory access보다 훨씬 느리기 때문에 응답시간에 영향을 줄 수 있다. 

처리
- 쿼리 최적화 
- `tmp_table_size` 를 늘려야한다 

#### Query count 
개념
- query execution 횟수
- 이 값이 낮은데 느리다면 조사해볼 가치가 있다. 

### 2. Metadata와 Application
쿼리 분석에는 query metric외에 metadata와 application도 알아야한다. 

메타데이터
- 최소한 아래 2개 메타데이터는 있어야한다
   1. 실행 계획 (`explain` plan)
   2. 각 테이블의 테이블 구조

애플리케이션
- 애플리케이션에서 이 쿼리의 목적과 왜 이 쿼리가 실행되는지 알아야한다

보통 이 정도를 통해서 분석을 위한 준비가 될 수 있는데, 때로는 외부 문제(neihbors problem)도 고려할 수 있어야한다. 

### 3. Relative values
배경
- 쿼리 메트릭에서 객관적으로 좋은 유일한 값은 0이다. 어떤 일을 가장 빠르게 하는 방법은 그 일을 하지 않는 것이기 때문이다. 
- 0이 아닌 값은 언제나 query와 application에 상대적이다. 

숫자에만 집착하는게 아니라 source code도 같이 볼 수 있다면, 데이터가 어떻게 사용되는지 파악할 수 있고, 이를 쉽게 최적화 할 수 있다. 

### 4. Average, Percentile, Maximum
배경
- query response time은 단일 value인 것처럼 말하는 것이 일반적이지만 실제로 그렇지 않다. 
- query metric은 query 별로 묶이고 집계되기 때문에 통계 정보를 기반으로 보고 된다 

값 - Average
- 지나치게 낙관적이다. 평균에 속으면 안된다. 

값 - Percentile
- average 보다 객적으로 대표성이 높고 덜 낙관적이다. 
- percentile을 쓰는 또 다른 이유는 무시되는 작은 비율의 value를 outlier로 간주하기 때문이다. 
- 가장 좋은 percentile은 P999(99.9%) 다. 0.1을 버리는것은 outlier가 실제로 존재할 수 있다는 현실적인 트레이드오프를 고려한 값

값 - maximum
- 어떤 value도 버리지 않음으로써 percetile 문제를 해결한다. 
- 어떤 사용자는 maximum query response time을 경험하고 서비스를 떠났을 수 있다. 
- P99에서는 잡을 수 없는 문제를 잡을 수 있다. 이를 통해서 쿼리의 문제를 찾을 수 있다. 

기타 
- minumum과 maximum 사이의 value distribution도 고려해보자. 

## Query Response Time 개선하기 
query optimization
- query response time을 개선하는 여정

### Direct Query Optimization
개념
- 직접 query 또는 index를 변경하는 것
- 이 작업으로 많은 문제를 해결할 수 있다. 

### Indirect Query optimization 
개념
- data와 access pattern을 변경하는 것. 
- query를 바꾸는 대신 query가 접근하는 대상과 방식을 바꾸는 것. 

예시
- 매일 대량의 데이터를 조회하는 쿼리
   - 테이블에 5억건의 데이터가 있다고 할 때, 데이터를 아카이브해서 최근 1주일 데이터만 남겨둔다 
- 캐시, 조회 모델을 통해서 접근 패턴을 컨트롤
- 반정규화 테이블을 만들어서 데이터 구조를 변경하는 방법

직접 쿼리 최적화를 먼저하고 문제가 해결되면 거기서 멈추면 된다. 그게 아니면 간접쿼리 최적화를 진행한다. 

## Query를 최적화해야 하는 시점
질문을 해보자
- "현재 query response time이 받아들일 만한가?" 
- 아니라면 쿼리 최적화를 계속해야한다

소프트웨어 엔지니어가 매주 메트릭을 검토하고 쿼리 프로파일을 통해서 최적화하는 것은 현실적이지 않다. 다만 아래 경우에는 최적화를 해야한다. 
1. performance가 고객에게 영향을 줄 때 
2. code 변경 전후 
3. 한달에 한번
   - code와 query가 변경 없더라도 data와 access pattern은 바뀐다. 
   - 이를 통해서 응답시간이 바뀔 수 있다. 

## MySQL을 더 빠르게 
query 나 application을 변경하지 않고 mysql을 더 빠르게 만드는 마법이나 비밀은 없다. 더 빠르게 만들려면 직접 쿼리 최적화와 간접 쿼리 최적화의 여정을 떠나야한다. 

## 요약
- performance는 mysql이 쿼리를 실행하는 걸리는 시간인 'query response time' 이다. 
- query response time은 의미있고, 처리 가능하기 때문에 mysql performance의 north start 다. 
- query metric은 slow query log 또는 performance schema에서 나온다. query metric source로는 performance schema가 가장 좋다 
- query metric은 normalized sql statement인 digest를 기준으로 묶이고 집계된다 
- query profile은 느린 query를 보여준다
- query report는 query 하나에 관해 이용될 수 있는 모든 정보를 보여준다. 쿼리 분석에 사용할 수 있다. 
- query analysis의 목적은 느린 response time을 해결하는게 아니라 query execution 을 이해하는 것이다. 
- query analysis는 아래 정보를 활용한다
   - report의 query metric
   - metadata: explain plan, table structure
   - application
- query optimization은 direct query optimization과 indirect query optimization으로 이어지는 두 부분의 여정이다. 
- 최소한 아래 경우에는 쿼리를 최적화 하자 
   1. performance가 고객에게 영향을 줄 때 
   2. code 변경 전/후
   3. 한달에 한번 query profile을 검토하고 느린 쿼리를 최적화한다
